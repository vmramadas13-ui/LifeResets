# Product discovery coverage audit

## Purpose and evidence

This audit maps the 186-question *LifeResets — Product Discovery Q&A* to the current build. The Q&A records product preferences and proposed capabilities; it is not proof that a feature exists or a command to enable a risky capability. The Product Requirements Document remains the acceptance source for behavior, privacy, accessibility, and release gates. The user's later clarification that iPhone is the primary device takes precedence over earlier Mac-first wording.

The Q&A says discovery is complete, but implementation is not. Its answers describe a much larger product than the current build. This audit deliberately omits personal measurements, creditor details, passwords, and other private values. The original Q&A stays in the owner's local Downloads folder; this sanitized crosswalk belongs in the public repository.

Status labels mean: **implemented** = present in the current code and aligned with the stated scope; **partial** = useful groundwork exists but acceptance details are missing; **not started** = no product implementation; **deferred** = intentionally held until a decision or security gate is met. Code on an unverified working branch is not called shipped or complete.

## Decisions to carry forward

- **Product and device:** A private personal planning system, used primarily on iPhone, with Mac support. The active development host is the user's MacBook M1; Q186's earlier ASUS setup preference does not describe the current machine. The intended hosting model is local-first on the laptop; remote iPhone access is through a private Tailscale connection, never an open public endpoint. The existing local web app does not yet provide that remote setup.
- **Planning and recovery:** Users own their goals and can change plans. Planning may suggest quests and adjustments, but consequential changes require a clear choice. Misses remain visible for learning, recovery is supportive, and XP is never erased as punishment.
- **THE CORE:** The intended assistant is called THE CORE and should use the user-selected, editable in-app address. It may help plan and propose bounded actions, but it cannot override the user's autonomy or take health, financial, external, or destructive actions without explicit safeguards and approval. The current implementation is a deterministic local fallback, not a configured generative AI.
- **AI provider direction:** Q59/Q60/Q169 select an intended multi-provider design: NVIDIA NIM, local Ollama, Gemini, with future OpenAI/Claude support and task-aware routing. No provider is configured by that preference alone. ChatGPT Go is not treated as an API entitlement; no free key, external call, or automatic provider switching is assumed.
- **Personal data:** Keep it local-first, permissioned, inspectable, exportable, and deletable. Awakening answers are optional and require separate `awakening_storage` consent; they are not sent to THE CORE. The current database is not encrypted at rest, so the UI warns against passwords, access codes, and exact health or financial details. Health and finance records still require separate, explicit controls; passwords and secrets remain out of chat and AI memory.
- **Visual direction:** The supplied Inkpop concept favors warm paper and calm daily planning. Discovery Q104/Q112/Q114 asks for a darker cinematic System interface and an anime-inspired character. Preserve the accessible, calm daily planner and treat a separate original System/character appearance as an optional visual layer; do not copy existing anime intellectual property. That second appearance is not implemented.

## Build order and release gates

Continue the PRD's build sequence and apply the discovery choices as acceptance context:

1. Character/progression, approval-gated task actions, the guided Awakening flow, configurable built-in life areas, and dated metric history are implemented on the feature branch; the last pushed commit passed GitHub CI run #35. Before applying branch migrations to the personal database, create and verify a separate backup.
2. Private Tailscale Serve is configured for this Mac and the local health endpoint passes over HTTPS. Complete the separate migrated preview, verify it on the physical iPhone, then finish laptop startup/recovery and scheduled encrypted backup/restore verification. Never enable public exposure as a shortcut.
3. Complete numeric baseline capture within Awakening, custom domain subareas, frequency-aware habit scheduling, guided review ceremonies, and the seven-day/90-day campaign checkpoints.
4. Agree on transparent XP, rank review, and optional demotion rules; then build attributes and the remaining character progression. Keep Life Score deferred until its formula and missing-data behavior are approved.
5. Add inspectable knowledge/memory and THE CORE provider integrations only after consent, provider retention/cost controls, deletion, and failure behavior are in place.
6. Build health, finance, and vault modules as separate permissioned areas with explicit export/deletion and recovery behavior; never mix vault secrets into chat or memory.
7. Add true offline edits/synchronization, notification preferences, external calendar scopes, and broader agent capabilities only after conflict handling, security boundaries, approvals, and audit evidence are ready.
8. Complete physical iPhone, larger-text, reduced-motion, keyboard/screen-reader, backup-restore, and release rollback checks.

## Current conclusion

The build follows the discovery on iPhone-first intent, local-first direction, supportive recovery, bounded approval, and initial character progression. It does not yet implement most of the requested product. The table above is the active crosswalk; the PRD's 40-story traceability table remains the acceptance checklist and must be updated as each slice is completed and verified.
